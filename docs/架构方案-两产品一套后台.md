# 架构方案 · 两个产品一套后台

> 方向性文档。当前只需落地手册（静态），美食地图后端待社群成型后再建。
> 本文定义**不变量**，避免将来又把两个产品做成两遍、或把校区硬编码导致无法复制。

## 一、核心不变量

1. **前端是可替换的壳。** H5 与未来的微信小程序共用同一套后端接口；换前端不换后端。
2. **数据收敛到统一层。** 手册内容、美食地图商户数据，都经由统一数据 / API 层提供，前端不直接写死业务数据。
3. **school 是租户，不是常量。** 校区 / 食堂 / 商圈不硬编码；将来可复制到武大、华科等任何学校。这是 FDE 样板工程的关键。

## 二、当前状态

- **手册**：静态 HTML + CSS + JS，内容写死在各页面（可接受，纯内容无需后端）。
- **美食地图数据**：`assets/foodmap-data/` 下 622 条本地 JS（`wuhan` 540 / `campus` 50 / `play` 32），带经纬度与评分字段。尚未接入任何服务。

## 三、推荐演进路径

- **阶段 A（现在）**：手册静态上线。美食地图数据先以本地 JSON / JS 沉淀，不接服务。
- **阶段 B（社群成型后）**：起统一 BFF（如 Next.js `/api` 或轻量服务），把 622 条商户数据对外提供只读 API；美食地图前端消费它。手册内容也可同期迁入同一数据层（Markdown / JSON），统一编辑。
- **阶段 C（小程序）**：重写 UI 层接同一 BFF；`profiles` 预留 `wx_openid`，微信登录平滑接入。

## 四、技术选型（待阶段 B 再定，先给方向）

- **数据层**：结构化内容用 Markdown / JSON；商户数据用同一存储。
- **BFF**：Next.js Route Handlers 或同等，前端永远不直连数据库。
- **多租户**：`school_id` 维度隔离；配置驱动主题与导航。

## 五、现在不做

- 不接 Supabase / 不建数据库（阶段 B 之前无必要，避免空转成本）。
- 不写死校区常量。
- 不为 UGC / 二手 / 动态圈预留表（需求未到）。

# 蛮有味 · 双轨智能体统一方案（确定性智能匹配 + DeepSeek 智能体，前端无感）

> **状态**：方案定稿稿（Robin 2026-08-15 大方向：算法层智能匹配为主，识别解决不了的问题路由到智能体；智能体接入用户自有 DeepSeek API；前端不露切换痕迹，统一展示智能体推演；界面重构按 product-restructure-design.md）。细节由 AI 补充，**待 Robin 确认后实施**。
> 关联：docs/SPEC.md §15 Q1/Q2/Q3/Q5、docs/design/product-restructure-design.md、docs/design/vision-adapter-design.md

## 1. 设计原则

1. **用户只看一个东西：蛮有味 Agent 的推演**。不管背后是确定性引擎还是 DeepSeek，前端呈现的是同一套「理解意图 → 检索 → 匹配 → 权衡 → 推荐」的渐进推演，**绝不出现"脚本模式/LLM 模式"字样**。
2. **实事求是**：匹配不出就是不硬凑——没有合适店铺时直说没有，或给出明确标注的「最接近选项」。
3. **双轨自动路由，用户零感知**：Tier 1（确定性，毫秒级、零成本、可审计）能搞定的直接出；Tier 1 自评"搞不定"才升级 Tier 2（用户自有 DeepSeek API，25s 护栏，失败自动回落 Tier 1 并诚实说明）。
4. **智能体框架轻量适配美食场景**：复用已有 agent-loop（ReAct + 10 工具 + finalize + 防幻觉 + 红线），只做场景化增强，不重造轮子。

## 3. Tier 1 · 确定性智能匹配增强（细化改动点）

### 3.1 意图解析增强（intent-parser.js）
| 能力 | 规则 | 示例 |
|------|------|------|
| 店名/关键词检索优先 | 无结构化信号（时段/价格/排序/片区词）时，整句（剥语气前缀）作为检索词 | 「老樊城」→ keyword=老樊城；「帮我找一家东北饺子馆」→ 东北饺子馆 |
| 健康饮食语义（FIT） | 健身/减脂/低脂/高蛋白/轻食/沙拉/增肌 → 检索词=FIT 词 + 口味约束「清淡」 | 「清淡的健身餐」→ keyword=健身餐 + taste=[清淡] |
| 口语同义词 | 已有 ORAL_CATEGORY_MAP，继续扩充本地口语（过早→早餐、撸串→烧烤…） | 「想撸串」→ 烧烤 |
| 口味约束提取 | 清淡/辣/酸/香酥/鲜… 进入筛选（tasteTags 匹配）而非仅展示 | 「清淡的」→ 候选仅 tasteTags 含清淡 |

### 3.2 候选检索策略（discovery-engine.js）
1. 店名包含匹配（name includes keyword）→ 命中即候选；
2. 未命中 → 模糊匹配（店名/招牌菜/口味/理由）；
3. 仍未命中且用户有口味约束 → **按口味约束给「最接近的真实选项」**，并诚实标注「非专门店，以实际菜单为准」；
4. 口味约束也 0 命中 → **直说没有，不硬凑**（degradation 明确文案）。
5. 命中后仍过口味/价格/时段约束叠加。

### 3.3 匹配质量自评（confident 信号，供路由判定）
对每次 Tier 1 结果输出质量信号（纯函数，可单测）：
- `keywordHit`：关键词是否命中（0/1）
- `tasteMiss`：口味约束 0 命中（0/1）
- `zeroMatched`：total_matched === 0（0/1）
- `constraintRich`：输入含 ≥2 类约束（片区+时段+价格+口味+场合，复合意图信号）
- `fitIntent`：含健康饮食语义（健身/低脂/高蛋白…）
- `fuzzyIntent`：无任何结构化信号且关键词未命中（纯模糊表达）

## 4. 路由判定（shouldUpgrade，规则 + 信号）

**升级条件（满足任一即升级 Tier 2，LLM 不可用时回 Tier 1）**：

| 信号 | 触发 | 理由 |
|------|------|------|
| keywordHit=0 | 未找到含「x」的店铺 | 关键词可能不在店名/招牌里，LLM 可语义检索（如"健身餐"→沙拉/鸡胸店） |
| zeroMatched=0 | 完全无匹配 | LLM 判断是否真有缺（数据缺口）或换个说法 |
| tasteMiss=1 | 口味约束无匹配 | LLM 做语义近似判断（如"清淡"→清蒸/粥/粤菜） |
| fitIntent=1 | 健康饮食语义 | 确定性引擎缺领域标签，LLM 结合常识检索（低脂高蛋白→鸡胸沙拉店） |
| fuzzyIntent=1 | 纯模糊表达 | 「心情不好想吃点治愈系」——LLM 情境理解是强项（PRD 已验证 H1） |
| constraintRich=1 且 keywordHit=0 | 复合约束 + 检索失败 | 多约束冲突需要权衡，LLM 做取舍 |

**护栏**：
- 升级前必须有 Tier 1 结果兜底（确定性结果保留在响应 `deterministicFallback`）；
- LLM 调用 25s 超时（Promise.race），失败/超时 → 回 Tier 1 + degradation 追加「AI 深度分析暂不可用」；
- LLM 结果仍需 resolveDecision 校验（防幻觉 id）+ redlineCheck；
- 成本护栏：仅升级场景调 LLM（日常结构化查询不触发），DeepSeek ≈2 分钱/次，校园量级月成本可控。

## 5. Tier 2 · DeepSeek 智能体（用户自有 API）

### 5.1 框架现状（已有，直接复用）
- ReAct 循环（agent-loop.js）：DeepSeek tool_calling → 10 领域工具 → finalize_recommendation（1 主推 + 2~3 备选 + reason + guidance）；
- 防幻觉：resolveDecision 校验商户 id 存在性，幻觉 id 丢弃；
- 红线：redlineCheck（PII/假坐标/伪造券/密钥）；
- 记忆：口味档案 /memory/:sessionId（多轮历史 history 已有）；
- 降级：AgentFallbackError → 自动回落确定性运行时（已有）。

### 5.2 美食场景适配（本次增强点）
1. **系统提示纪律 v2**（agent-loop buildMessages 强化）：
   - 排序只基于信任信号（评分/距离/人均/真实点评），绝不因付费改变；
   - 推荐理由必须落到具体事实（招牌菜/人均/环境/距离），禁编造评分与距离；
   - **数据中没有完全合适的店铺时，必须明说"数据库没有完全符合的"，再给最接近选项并标注差异**（对应 Q1 实事求是）；
   - 距离与片区口径与确定性引擎一致（CAMPUS_COORDS / distKm）。
2. **finalize_recommendation 增加可选 `note` 字段**：诚实声明/数据缺口说明（如"数据库没有健身餐专门店，这家是最近的清淡选择"），前端在推荐卡顶部渲染（不遮挡主推）。
3. **工具使用约束**：先 search_merchants 收窄再 finalize（已有）；检索词失败时允许尝试 2~3 个语义近义词（新允许）。
4. **多轮追问**：history 已回灌；「换一家/再便宜点/换个附近」由会话状态（exclude/maxPrice/zone）承接（已有 S6 追问条）。

### 5.3 智能体框架边界（明确不做）
- 不做多智能体编排、不做复杂规划——单轮决策 + 多轮会话已覆盖"今天吃啥"；
- 不做流式输出——统一推演展示由前端阶段化渲染（见 §6）；
- 不做长记忆学习——口味档案按会话隔离即可。

## 6. 前端统一推演展示（无切换痕迹）

### 6.1 阶段模板（前端唯一对外形态）
```
① 理解你的意图  → ② 检索数据库  → ③ 匹配你的条件  → ④ 排序与权衡  → ⑤ 生成推荐
```

### 6.2 双路径 → 阶段映射（前端纯函数 buildRevealSteps(trace)）
| 阶段 | 确定性 trace（/run） | LLM trace（/agent） |
|------|----------------------|---------------------|
| ① 理解意图 | kind=intake（detail：片区/品类/时段/关键词） | tool 步骤前 thinking（模型复述意图）或首个 action 前 |
| ② 检索数据库 | kind=filter（命中 N 家，口径） | action=search_merchants（找到 N 家候选） |
| ③ 匹配条件 | filter detail（约束清单） | action=filter/rank（按条件收窄） |
| ④ 排序与权衡 | kind=geo/rank（就近/排序/缺口） | action=rank/get_merchant_detail（核对细节） |
| ⑤ 生成推荐 | kind=decide/why（主推+理由+因子） | finalize（提交决策，reason/note） |
| 澄清 | — | kind=question → Agent 提问气泡（用户回答后继续） |

### 6.3 渐进式呈现（Q1「让用户感觉智能体在运行」）
1. 提交后**立即渲染 5 阶段骨架**（"分析中"脉冲动画，每阶段标题可见）；
2. 响应到达（Tier 1 毫秒级 / Tier 2 数秒）后**逐阶段点亮**：每阶段展示真实内容（关键词/命中数/口径/理由），间隔 ~350ms，总时长 ≈1.5s（Tier 1 也保持节奏，避免"秒出结果=没分析"的观感）；
3. 点亮完成 → 主推卡淡入 + 备选卡 + 「为什么推荐」因子权重条 + 多轮追问条（S6 已有）；
4. **无来源标签**：不显示"脚本/确定性/LLM/升级"，只显示「蛮有味 Agent 推演」+ 可回放哈希（provenance 保留，作为信任内核证据而非模式标签）；
5. 诚实空态：0 匹配/无合适 → 阶段 ⑤ 显示「没有符合条件的店铺」+ 说明（LLM note 或确定性 degradation 文案）。

### 6.4 实现要点
- 纯函数 `buildRevealSteps(trace)`（可单测：确定性与 LLM 两类 trace 分别断言阶段映射正确）；
- 骨架/点亮/淡入动画用 CSS（tokens 变量），无第三方动画库；
- 与界面重构（P1 首页重构）一起上线。

## 8. 风险与护栏

| 风险 | 护栏 |
|------|------|
| DeepSeek 网络不稳（本机实测偶发失败） | 25s 超时 + 失败回落 Tier 1 + 诚实说明；前端永不转圈超 25s |
| LLM 幻觉（编店铺/编评分） | resolveDecision id 校验 + redlineCheck + 系统提示纪律 v2 |
| LLM 成本 | 仅升级场景调用；每日次数日志可审计；后续可切智谱 glm-4-flash 免费文本兜底（同一 OpenAI 兼容层） |
| 用户感知割裂 | 统一阶段模板 + 无来源标签 + 渐进渲染；provenance 哈希保留为信任证据 |
| 界面重构丢商业化 | 福利 Tab 常驻底部 + 入口显眼；券包/核销/签到完整迁移 |

## 2. 产品定位

**一句话**：武汉 & 财大周边的美食集散平台——帮同学按场景找到喜欢的好吃，帮商家通过平台主动收录 + 优惠券获得客流与曝光。

**两个用户，两个价值**

| 用户 | 核心诉求 | 我们提供 |
| --- | --- | --- |
| 学生 / 在校生 | "现在想吃顿好的 / 宵夜 / 便宜的，附近有啥？" + "想攒点优惠券" | 就近/场景/口味发现 + 榜单 + 导航 + **账号与云端收藏** + **签到/玩法得券 + 券包** |
| 商家 | "想被更多同学看到、带来客流" | **平台主动收录** + **合作发券（到店核销打折）** + 未来排行榜曝光 |

**不做（v1 边界）**：UGC 长点评、社交动态圈、积分商城、商家自助认领后台（认领明确不做）、付费广告投放后台。

## 4. 核心功能设计

### 4.1 学生侧"找到喜欢的美食"
- **就近**：校区（首义/南湖）默认视角，按到校区距离排序；"全城"为探索视角。
- **按场景**：`mealTime`（早/午/晚/夜宵）快捷入口——数据已有但大量空缺，需补全。
- **按口味**：统一分类法（§6）+ `cuisine` 细分。
- **榜单**：必吃榜（rating=必吃）、性价比榜、夜宵榜、新收录。
- **搜索**：店名/招牌菜/地址/理由模糊匹配。
- **收藏（云端）**：登录后收藏存服务端，跨设备同步。未登录可本地临时收藏，登录后合并。
- **个性化（演进）**：v1 用"收藏 + 最近看 + 场景筛选"模拟；接账号与行为数据后做偏好学习。

### 4.2 商家侧"提高曝光"（平台主动，认领不做）
- **① 平台主动收录（v1 起）**：编辑/地推主动录入并补全信息，信息越全越易被搜到、越可信。**不做商家自助认领**（避免单独做商家版 App）。
- **② 优惠券合作（早期核心）**：与商家谈折扣 → 平台发券 → 学生得券到店核销打折。是早期引流 + 双边启动手段。券的"获得方式"由奖励引擎统一调度（见 §4.5）。
- **③ 排行榜（演进，v2）**：从编辑精选起步，随浏览/领券/核销数据积累演进为数据驱动真实性排行榜。
- **付费推荐位**：后置到流量验证后。

### 4.3 优惠券闭环（早期核心 ★）
**闭环**：平台创建券（绑定商家/平台通用、折扣说明、库存、有效期、每人限领）→ 学生通过"玩法"得券（v1 = 签到）→ 生成**含券码+用户ID+时效的二维码** → 到店出示 → 商家核销 → 标记已用。

**v1 得券来源 = 签到（§4.5）**：学生每日签到累积连续天数，按档位发放通用券；连续满 7 天给额外奖励券。这是平台早期冷启动的流量引擎——学生有理由每日来、商家获得持续客流。

**核销早期间化（不做商家 App）**：
- 商家侧：平台提供**简易核销网页**（扫码/输码标记已用），或微信扫一扫识别平台核销链接；极小规模可线下对账（报手机号尾号）。
- 学生侧：我的券页展示二维码 + 状态（已得/已核销/已过期）。

**防刷与安全（P0，见 §8）**：券绑定用户、一次性、短时效、领取限频；核销幂等；库存防超发；签到防作弊（同设备/同日不可重复、异常频率限流）。

### 4.4 账号体系（★v1.5 核心）
- **登录/注册**：优先**微信网页授权一键登录**；手机号/邮箱+密码兜底。
- **信息安全**：密码 Argon2/bcrypt 哈希；HTTPS；JWT/Session 安全；手机号/邮箱脱敏。
- **云端收藏与券包**：收藏、得券记录服务端保存，跨设备同步。

### 4.5 奖励引擎（玩法可插拔架构 ★v1 新增，本方案核心抽象）
**目标**：券的"获得方式"是可扩展的。v1 只实现**签到**，但架构预留抽奖/任务/直接领，后续加玩法不改核心、只挂插件。

**核心抽象**
- `RewardEngine`：注册并调度 `PlayPlugin`（玩法插件），提供统一入口 `participate(playId, userId, ctx)`。
- `PlayPlugin` 接口（所有玩法实现统一契约）：
  - `id` / `name` / `desc`：玩法标识与展示信息
  - `getStatus(userId)`：返回当前进度（如签到连续天数、今日是否已签）
  - `canParticipate(userId, ctx)`：资格校验（限频/防重复）
  - `participate(userId, ctx)`：执行业务，**调用 `CouponIssuer` 发券**，返回所得券 + 新状态
  - `render(ctx)`：返回该玩法的 UI 片段（签到日历/抽奖转盘/任务列表），由宿主页嵌入
- `CouponIssuer`：统一发券——生成券记录（code、来源玩法 `play_type`、折扣、有效期、状态），与 §4.3 闭环衔接。
- `RewardStore`：数据访问抽象，隔离"现在 localStorage / 将来 BFF"。`localStorageStore`（v1 原型实现）与 `bffStore`（v1.5 实现）实现同一接口，引擎不感知底层。

**v1 玩法清单**
| 玩法 id | 名称 | 状态 | 说明 |
| --- | --- | --- | --- |
| `checkin` | 每日签到 | **已实现（v1）** | 连续签到得通用券，满 7 天额外奖励 |
| `lottery` | 抽奖得券 | 预留接口 | 未来：消耗积分/次数抽券 |
| `task` | 任务得券 | 预留接口 | 未来：完善资料/首次收藏/邀好友等任务 |
| `claim` | 直接领商家券 | 预留接口 | 未来：商户详情页一键领券（对应 §4.3 领券按钮） |

> 设计要点：新增玩法 = 新建一个 `PlayPlugin` 文件 + 向 `RewardEngine.register()` 注册，**不改动引擎与券包**。这是"模块抽离、方便加不同玩法"的落地。

## 6. 数据治理（上线前必做 + 持续补充）

审计实测（2026-08-06）：
- `wuhan.js` 540 条：**"五谷杂粮"错配为默认分类 81 条**；混入 **"南湖推荐" 69 条**造成分类命名冲突。
- `rating` 空缺 **355/540（66%）**；`avgPrice` 空缺 83/540。
- `campus.js` 52 家：41 家缺 rating、40 家缺 avgPrice。
- `play.js` 32 条字段独立，需与商户表统一。

**治理动作**
1. 统一分类法（草案）：早餐 / 小吃宵夜 / 火锅 / 烧烤 / 烤肉 / 湖北菜 / 湘菜 / 川菜 / 粤闽潮汕 / 日料烧鸟 / 韩餐 / 泰越等异国 / 西餐 / 面包甜点 / 私房菜 / 苍蝇馆子 / 自助 / 其他。重归类错配项；解决"南湖推荐"跨源冲突。
2. 补全 `rating` / `avgPrice` / `mealTime` 空缺，优先财大周边 52 家与高频场景字段。
3. 三源合并为商户表 + 玩乐表，加治理字段。
4. **持续补充数据**：建立录入规范 + 校验脚本（检测非法分类、坐标越界、必填空缺），防回归。

## 7. 前端方案（优雅 + 薄壳可换壳）【已定：Vite 轻构建】

**非功能硬要求**：长期产品，视觉与交互须**优雅**——设计系统（design tokens：色板/字阶/间距/圆角/阴影）、精致组件、流畅动效、响应式、基础无障碍。视觉严格遵循 §1 蛮有味规范（印章红/宣纸/墨绿，Ma Shan Zheng 字标）。

**工程选型（A'，已确认）**
- **Vite + 原生 JS/TS 模块化**（不引入 Vue/React 重框架）。保持"薄壳、可换壳、易转小程序"不变量，又获模块化/可打包工程能力。
- 独立写一套蛮有味主题 CSS（design tokens），不与手册混用。
- **保留转小程序**：逻辑用 Web 标准，未来套壳仅做适配层（导航/登录用 `wx` API 替换）。

**被否方案**：复活被删 `platform/` 模块化空壳架构（那是被删的脚手架，不值得重建）。

## 8. 安全（P0）

- **高德 Key 明文入库（高危）**：移出仓库——环境变量 + 构建注入，或后端代理转发。
- **账号安全**：密码 Argon2/bcrypt 哈希；HTTPS；JWT/Session 安全；微信 OAuth 校验 `state` 防 CSRF；手机号/邮箱脱敏。
- **优惠券/玩法防刷**：券绑定用户、一次性、短时效、限频；核销幂等；库存原子扣减；**签到防作弊**（同设备/同日不可重复、异常频率限流）。
- **注入/XSS**：DB 查询参数化；渲染用文本节点而非 `innerHTML` 拼店名；用户输入（搜索/注册）校验长度与类型。
- **密钥管理**：高德 Key、微信 AppSecret、JWT 密钥均不入库、不进前端包。

## 13. 开发看板（模块拆分 + 验收标准）★ 自动循环的唯一事实来源

> 本節是「守门智能体」每轮循环读取的目标。每个模块含：目标 / 交付文件 / 验收标准（可测）/ 依赖 / 状态。
> 状态词汇：`已完成` / `进行中` / `待开发` / `受阻`。智能体每轮只推进**一个**模块，完成后把状态改为 `已完成` 并在 `.workbuddy/memory/` 当日日志追加一条，遇阻改 `受阻` 并写明根因与缺信息。

### 13.1 开发循环协议（守门智能体必须遵守）
1. **取任务**：读本节状态表，按模块序号挑第一个 `待开发`（或 `进行中`）模块。
2. **开发**：按其「交付文件」实现，严格复用现有架构——引擎逻辑放 `src/core`、`src/plays`；UI 放 `src/ui` 且用 `src/ui/dom.js` 的 `h()` 安全渲染（禁止 `innerHTML` 拼接动态内容）；视觉只用 `src/styles/tokens.css` 的 CSS 变量。
3. **测试**：
   - 纯逻辑改动 → 在 `h5/test/` 增/改 `*.test.mjs`（localStorage shim 已示范），运行 `/Users/onebilion/.workbuddy/binaries/node/versions/22.22.2/bin/node test/xxx.mjs` 须全绿。
   - 所有 JS → `node --check` 语法校验全过。
   - UI/页面改动 → 起静态服务（`/usr/bin/python3 -m http.server 5180`）后 `curl -o /dev/null -w "%{http_code}"` 校验 `index.html` 与改动文件返回 200。
4. **验收**：对照本节「验收标准」逐条确认；UI 类列出人工验收清单（无法无头点击时，至少保证可加载、无控制台报错模式、DOM 用 `h()` 构建）。
5. **反馈**：更新本节状态 + 当日 memory 日志；若同根因失败 2 次 → 改 `受阻`，停止盲试，写明已确认现象/根因/已尝试/缺信息/建议下一步，等人工。
6. **红线（绝不越界）**：不 `git push` / 不部署 / 不改密钥环境变量 / 不删数据；涉及付费、对外发布、不可逆操作先停。高德 Key、微信 AppSecret、JWT 密钥任何时候不入库不进前端包。
